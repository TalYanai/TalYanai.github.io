An AI assistant that can read my university data, and nothing else

Applied AI · Model Context Protocol · Claude Code
Problem
Deadlines, forum posts and grades are spread across many course pages, and I wanted an assistant that can read them without being able to change anything.
What I built
A local MCP server over the Moodle web-services API with eight read-only tools: courses, deadlines, assignments, grades, course contents, forum discussions, submission status and file download. It is registered in Claude Code and feeds a study-planning workflow and scheduled status checks.
Safeguards
The access token sits in Windows Credential Manager, is removed from any output, and logging is silenced because download links carry it. Requests are throttled and every ID is validated. No browser automation or stored cookies.
Evidence
A live call listed my courses from the running server.
Limits
Local only, not packaged, no automated tests, and tied to a token that the university can reset.

TYFitness — a training dashboard whose numbers I can check

Product · data checks · MCP · Cloudflare
Problem
Garmin's own apps do not combine my running, strength and race goals in one place, and I wanted numbers I could trust.
What I built
A single-user dashboard that combines my running, strength and race goals. A scripted refresh pulls workouts from Garmin through a read-only connection limited to three tools, builds the dataset, and recomputes the key figures independently as a check before publishing. Manual records and targets are stored separately, so a refresh never overwrites them. I specified the behaviour and the checks and built it with AI coding assistants.
Operations
The data is behind a password with a lockout after five wrong attempts. The refresh runs as one command and on a weekly schedule.
Evidence
Live on Cloudflare Workers, with the data endpoints returning 401 without a login. The verify script recomputes monthly and weekly counts, record times and goal progress from the raw files, and all checks pass.
Limits
One user, no unit-test suite beyond the verify script, no CI, and it depends on a third-party Garmin MCP server. The live app is private because it holds personal health data.

GymLog V2 — a workout log that works without a signal

Product · offline-first · Cloudflare · open source
Problem
Workout apps lose entries without a signal in the gym, and I wanted to import my own Garmin history and keep the data in my hands.
What I built
A progressive web app that works offline and keeps its data on the device behind a validated schema. A small sync service keeps copies consistent: changes are versioned, retried requests are safe, conflicts are reported and deletions are kept as markers. It also imports Garmin history and has backup and restore with integrity checks. I specified the behaviour and built it with AI coding assistants; the tests check it.
Evidence
91 automated tests pass in under two seconds. They cover sync authentication, conflicts, concurrency, tombstones and paging. A deploy script checks the token, runs the tests, builds and verifies. The app has no runtime dependencies.
Limits
Single user with one shared bearer token, not per-user accounts. No CI workflow yet. The sync tests run against a D1 test helper rather than a live D1. The interface is in Hebrew.

n8n — PartyPlanner AI: a two-agent invitation workflow

n8n · Claude Sonnet · Gmail · university group project
Context
A university team project. Teammates built the web front end that collects the party details. My part was the n8n automation and agent layer.
How it works
A webhook receives the party data, a code node cleans the inputs, and a validation step checks the required fields before any model is called. A Designer agent drafts the invitation wording, a template service renders the image, and a Sender agent with two scoped Gmail tools sends the invitation to guests and, separately, the shopping list and task checklist to the organiser only. Failed validation emails the organiser or returns HTTP 400, and an error trigger alerts an admin.
Iteration
I exported 13 versions between 8 and 14 June 2026. The workflow moved from one prompt-driven agent to two single-purpose agents, and the deterministic image step moved out of the model into a plain node.
Known limits
From a static review of the final export: the Designer's output is not wired into the image step, validation in practice checks only the organiser's email, the fallback branch is fragile, and the in-workflow error trigger is probably inert. There is no run history, so I do not call this production.

Make — sign-up automation and an AI assistant for a community organisation

Make · Monday.com · FastBots · WhatsApp
Problem
A community organisation that runs small neighbourhood meetings handled sign-ups, duplicate checks, reminders and host recruitment by hand on top of its Monday.com boards. I worked from a specification of six scenarios: open meeting, waitlist, host recruitment, personal commitment, post-meeting follow-up and risky leads.
What I built
Seven Make scenarios, 147 modules in total, all event-driven. They cover host and attendee sign-up intake, a board-triggered messaging scenario, a 57-module duplicate check, a button that counts group members per category, and two scenarios that connect the boards to the assistant. Four scenarios use retry handlers, and one writes failures to a spreadsheet.
The assistant
A WhatsApp-style assistant prototyped in FastBots with a written instruction set. It detects one of five intents, asks one question at a time, replies in the user's language, and returns structured output for Make to process. Host recruitment has two pass-or-fail gate questions and a nine-question scoring form. It holds no event data of its own: real details arrive only as named commands from Make. A risk policy escalates credential requests and prompt-injection attempts to a person at once, and gives softer signals one warning first.
Status
The scenarios exist as complete exported blueprints. Whether they ran in production, and for how long, is not verified, and I have no usage numbers. Two of the six specified scenarios (personal commitment and post-meeting follow-up) have no scenario. The assistant is a documented prototype.
Privacy
No organisation, people, boards or links are named here.
